## Раздел A. Физика, топология, параметризация

### DL-16. GND должен повторять контур подложки — не bbox
- **Когда:** замечание пользователя после v1.5.0 / v1.6.2.
- **Симптом:** GND — один прямоугольник по bbox; подложка — ступенчатый union. Фольга торчит за контуром платы.
- **Первопричина:** bbox-GND выбран для простоты, но не соответствует реальной PCB.
- **Исправление:** GND — union прямоугольников, совпадающих с подложкой + мостики.
- **Урок:** GND — физический слой, строить в паре с подложкой.

### DL-17. TRL-длины зависимы от `L_thru` для сдвига reference plane
- **Симптом:** `L_ref`, `L_feed` — без связи с `L_thru`; reference plane не сдвигалась.
- **Первопричина:** не учтено требование TRL: reference plane на центр THRU; фидеры резонатора — de-embedding на TAB.
- **Исправление:** `L_ref = L_feed = L_thru/2`; OPEN-порты в плоскости LINE-портов; `deembed = L_thru/2` для RES; зазор OPEN = `dL`.
- **Урок:** в TRL все длины — производные от `L_thru`.

### DL-18. Учёт посадочных мест end-launch 1.85 мм (Gigalane) в компоновке
- **Симптом:** оценочный зазор не соответствует реальному посадочному месту разъёма 1.85 мм.
- **Первопричина:** компоновка «на глаз» без привязки к физической посадке разъёма.
- **Исправление:** `conn_pin_offset = 4.24`, `conn_ins_depth = 5.08`, `conn_flange_w = 12.7`, `conn_hole_pitch = 9.53`, `conn_hole_dia = 2.0`. Все структуры удлинены; GND-keepout.
- **Урок:** при компоновке платы под конкретный разъём — брать габариты из drawing.

### DL-19. Физическая модель коаксиального разъёма: диаметры, длина λ, симметрия
- **Симптом:** абстрактные Wave Port на краю платы; порты не симметричны.
- **Первопричина:** не моделировалась внутренняя часть разъёма.
- **Исправление:** Отрисовка коаксиала (`r_pin_coax`, `r_diel`, `r_outer`); точные диаметры (0.13, 0.23, 0.75, 1.85 мм); `L_coax = 150/f0_GHz`; Wave Port на торце.
- **Урок:** для коаксиальных разъёмов моделировать внутреннюю часть длиной ≥ λ/4.

### DL-24. Пины должны выходить наружу и перекрывать линию
- **Симптом:** пины рисовались внутрь; линии не менялись от `f0_GHz`.
- **Первопричина:** пин уходил внутрь коаксиала; длины передавались числами.
- **Исправление:** пин перекрывает пад на 1 мм; `L_line = "L_thru + dL"`; посадочные места через HFSS-выражения.
- **Урок:** пин заходит на плату; для параметризации — HFSS-выражения.

### DL-26. Стенка разъема должна смотреть наружу, а не внутрь платы
- **Симптом:** стенка разъема перекрывала сигнальную линию и посадочные места.
- **Первопричина:** неверная координата `origin`.
- **Исправление:** Точка начала стенки смещена наружу от края платы. Размер `conn_ins_depth` всегда положительный.
- **Урок:** при создании объемов размеры должны быть положительными. Для отрисовки «наружу» менять `origin`.

### DL-27. Ширина лапок разъема (земли) = (12.7 - 6.35)/2 = 3.175 мм
- **Симптом:** лапки разъема занимали всю ширину фланца.
- **Первопричина:** неправильное чтение чертежа (6.35 мм — это ширина окна под сигнал).
- **Исправление:** `leg_width = (conn_flange_w - conn_gnd_gap)/2 = 3.175 мм`. Лапки отрисовываются отдельно слева и справа.
- **Урок:** внимательно читать размеры на чертеже.

### DL-28. Разделение шага `pitch_trl` и `pitch_res`
- **Симптом:** расстояние между TRL и резонатором было жестко зашито.
- **Исправление:** введены отдельные переменные `pitch_trl` и `pitch_res`.
- **Урок:** выносить координаты ключевых узлов в отдельные переменные для гибкости.

### DL-29. Увеличение ширины мостика до TRL, ширина стенки 12.7 мм, лапки 2.5 мм
- **Симптом:** мостик был уже, чем подложки TRL; стенка уже фланца; лапки не доходили до падов.
- **Исправление:** `Bridge_3` = `L_line + 2*conn_ext`. Стенка = `conn_flange_w` (12.7 мм). Высота лапок = `2.5 мм`.
- **Урок:** при стыковке структур использовать максимальную ширину.

### DL-30. Z-смещение коаксиала для пересечения с полоском на 8 мкм, лапки точно на TopPad
- **Симптом:** пин не пересекался с полоском; лапки не доходили до TopPad.
- **Исправление:** `z_coax = h + t_cu - 0.008mm + r_pin_coax`. Длина лапок `leg_y_size = 2*conn_ins_depth`.
- **Урок:** для гальванической связи пина с полоском в HFSS необходимо моделировать их взаимное проникновение (overlap).

### DL-31. Отверстия только в ПП, а не в лапках. Пазы вместо цилиндров.
- **Симптом:** Лапки разъема имели круглые отверстия, что физически неверно.
- **Исправление:** Убрано вычитание из лапок/стенки. Форма отверстий изменена с цилиндров на пазы.
- **Урок:** Крепежные элементы разъема не должны иметь сквозных отверстий.

### DL-32. Длина TopPad 5.58 мм, отступ центра паза 3.0 мм от края ПП.
- **Симптом:** Размеры посадочного места не соответствовали чертежу.
- **Исправление:** Введен параметр `pad_size_y = 5.58` мм. Отступ `conn_hole_x` = `3.0` мм.
- **Урок:** Все размеры посадочных мест брать строго из чертежа.

### DL-33. Формирование овального паза (obround) через два цилиндра и Box.
- **Симптом:** Прямоугольный паз (Box) не соответствовал чертежу.
- **Исправление:** Создание двух цилиндров, объединение их с промежуточным Box, вычитание из ПП.
- **Урок:** Для создания пазов со скругленными концами использовать `unite` двух цилиндров и бокса.

### DL-34. Пазы должны быть ориентированы вдоль лапок (по оси Y) для люфта при монтаже.
- **Симптом:** Паз был повернут на 90 градусов (вытянут по X).
- **Исправление:** Смещение цилиндров перенесено на ось Y.
- **Урок:** Ориентация паза имеет значение. Пазы вытянуты вдоль оси Y для технологического люфта.

### DL-36. Заливка GND_TOP перекрывала микрополоски. Замена на локальные площадки
- **Симптом:** Заливка верхнего слоя земли (GND_TOP) перекрывала сигнальные линии и приводила к КЗ.
- **Первопричина:** попытка сделать сплошную заливку GND_TOP.
- **Исправление:** Полностью убрана сплошная заливка GND_TOP. Созданы локальные прямоугольные площадки `TopPad`.
- **Урок:** На верхнем слое платы в области посадочных мест ВЧ-разъемов лучше использовать локальные земляные площадки (GCPW).

### DL-37. Прямоугольные пады (вместо цилиндров) на конце полоска для стыковки с пином
- **Симптом:** Цилиндрические пады создавали полукруглые выступы на конце полоска.
- **Исправление:** Пад выполнен в виде прямоугольного Box-а, объединенного с сигнальной линией.
- **Урок:** Форма контактной площадки в зоне перехода на коаксиал должна быть прямоугольной.

### DL-41. Параметр `pitch_trl` перестал работать из-за захардкоженных `x_*_val`
- **Симптом:** При изменении `pitch_trl` в `Design Properties` линии и подложки сдвигались, а разъемы (порты, стенки, TopPad) оставались на месте.
- **Первопричина:** При исправлении DL-39 (Parasolid Error) ассистент передал в `create_box` для `TopPad` и в `create_coax_and_port` числовые значения вместо HFSS-выражений.
- **Исправление (v2.5.2 / v2.5.4):** В функцию `draw_coax_and_port` добавлен аргумент `x_expr` (строка HFSS-выражения) для геометрии и `x_num` (число Python) для `integration_line` порта.
- **Урок:** При передаче координат в `create_box` / `create_cylinder` / `create_rectangle` нужно передавать **строку-выражение** HFSS, если требуется параметризация. Python-числа передавать только в API, которое требует `float`.

### DL-42. Параметр `f0_GHz` перестал работать из-за захардкоженных `L_line_val`, `r_mean_val`
- **Симптом:** При изменении `f0_GHz` в `Design Properties` менялись только `L_thru` и `L_coax`. `L_line`, `r_mean`, `r_out`, `r_in`, `r_tab_in`, `r_tab_out`, `y_top_res` оставались неизменными.
- **Первопричина:** Ассистент, пытаясь избавиться от `Parasolid Error` (DL-39), перевел все вычисления в Python и присвоил переменным HFSS готовые числа.
- **Исправление (v2.5.4):** Возвращены HFSS-выражения для `L_line`, `r_mean`, `r_out`, `r_in`, `r_tab_in`, `r_tab_out`, `y_top_res`. Python-числа оставлены только для `integration_line` портов.
- **Урок:** Параметризация HFSS-переменных требует, чтобы все зависимости были выражены через `hfss["..."] = "..."`, а не через Python-числа.

### DL-44. Избыточный объект `Pad` на сигнальных линиях
- **Когда:** v2.5.6.
- **Симптом:** На конце каждой сигнальной линии создавался прямоугольный объект `Pad_{name}`.
- **Первопричина:** Ошибочное предположение, что для гальванической связи пина с линией требуется дополнительный пад.
- **Исправление:** Удалено создание `Pad_{name}`. Сигнальные линии объединяются напрямую с пинами.
- **Урок:** Если два металлических объекта пересекаются в 3D (пин и линия перекрываются по Z на 8 мкм), дополнительный Pad не требуется.

### DL-45. `Solid ID assignment finds tets without bodies` — некорректный порядок вычитаний коаксиала
- **Когда:** v2.5.6, при первом запуске `Analyze`.
- **Симптом:** `Solid ID assignment finds 18109 tets without bodies`.
- **Первопричина:** Ошибочный порядок вычитаний в `draw_coax_and_port`: диэлектрик (содержащий пин) вычитался из оплётки/стенки/крышки, из-за чего внутри металла оставался «кусок пина». Плюс дублирующее тотальное вычитание проводников из диэлектриков.
- **Исправление (v2.6.0):** Правильный порядок:
  1. Создать 3 сплошных цилиндра (`pin`, `coax_diel`, `coax_outer`).
  2. Создать `wall` и `cap`.
  3. Вычесть `coax_diel` (сплошной) из `coax_outer`, `wall`, `cap`.
  4. Вычесть `pin` из `coax_diel`.
  5. Убрать взаимные вычитания и тотальное вычитание проводников из диэлектриков.
- **Урок:** В коаксиале порядок вычитаний критичен. Сначала вычесть диэлектрик (сплошной) из металлов, затем пин из диэлектрика. Не дублировать вычитания в глобальном блоке.

### DL-46. Ренормализация `renormalize=True` на портах коаксиала искажала импеданс
- **Когда:** v2.6.0.
- **Симптом:** Порты коаксиала с `renormalize=True` принудительно нормировали импеданс к 50 Ом, искажая физическую картину перехода.
- **Исправление (v2.6.1):** `renormalize=False`. HFSS использует характеристический импеданс самой линии (Zpi).
- **Урок:** Для коаксиальных портов использовать `renormalize=False`, чтобы сохранить физический импеданс перехода.

### DL-47. `Both endpoints of port lines must lie on the port` — рассогласование HFSS-выражения и Python-числа
- **Когда:** v3.4.0, первый вызов `create_port_and_wall` (`P_THRU_1`).
- **Симптом:**
  ```
  [error] port 'p_thru_1': both endpoints of port lines must lie on the port.
  IntLine: Start=['-25.0mm', '-5.0mm', '0.93mm'], End=['-25.0mm', '-5.0mm', '0.0mm']
  ```
  Лист порта создан по HFSS-выражению `origin=["(x_thru) - port_w/2", "-L_thru/2", "0mm"]`, а `integration_line` передавался как Python-число `-5.0`.
- **Первопричина:** HFSS-парсер вычислял `-L_thru/2` в `origin` с внутренней точностью, отличной от Python-числа `-L_thru_val/2 = -5.0`. Разница в последних знаках приводила к тому, что точка `(-25, -5, 0.93)` оказывалась «чуть вне» плоскости порта.
- **Исправление (v3.4.1):** Все координаты листа порта формируются через `"{:.6f}mm".format(value)` — те же Python-числа `x0`, `y0`, `z0`, что идут в `integration_line`. Никаких HFSS-выражений в `origin` листа.
- **Урок:** Для листа порта и его `integration_line` использовать **одни и те же числовые значения**. Не смешивать HFSS-выражения и Python-числа.

### DL-50. Удаление разъёмов и переход к чистым микрополосковым портам (v3.x)
- **Когда:** v3.0.0 — запрос пользователя: «Убери рисование разъемов. На концах полосковых линий микрополосковые порты расставь».
- **Симптом:** Модель с разъёмами — источник ошибок сетки (`Solid ID assignment`, `intersect`) и лишних граничных условий.
- **Первопричина:** Разъёмы нужны только для сравнения «симуляция–измерение», но не для расчёта S-параметров калибровочных мер.
- **Исправление (v3.0.0):** Убраны все объекты разъёмов. Порты — прямоугольные листы на краях линий. Воздушное окружение — Open Region. Padding = 0 на сторонах портов (+Y, -Y) и земли (-Z).
- **Урок:** При разработке калибровочных мер и параметрических исследований — начинать с идеальных микрополосковых портов, а разъёмы добавлять только для верификации.

### DL-51. `Both endpoints of port lines must lie on the port` — порт не на границе Open Region
- **Когда:** v3.4.1, первый вызов `create_port_and_wall("THRU_1", …)`.
- **Симптом:**
  ```
  [error] port 'p_thru_1': both endpoints of port lines must lie on the port.
  IntLine: Start=['-25.0mm', '-5.0mm', '0.93mm'], End=['-25.0mm', '-5.0mm', '0.0mm']
  ```
  При этом `origin` листа порта и `integration_line` сформированы из **одинаковых** Python-чисел (`-5.0` в обоих местах). DL-47 здесь ни при чём.
- **Первопричина:** `create_region` задан с `pad_value=["15mm", "15mm", "0.5mm", "0.5mm", "15mm", "0mm"]`. Padding `0.5 мм` на `±Y` сдвигает границу Region на `y = ±(L/2 + 0.5)`, а лист порта создан на `y = ±L/2`. В HFSS `Wave Port` **обязан лежать на внешней границе** 3D-задачи (мануал HFSS 2025 R2, раздел «Wave Ports»: «A wave port is restricted to reside at an external boundary of a 3D problem»). Порт «внутри» объёма → HFSS отвергает интеграционную линию, даже если она геометрически лежит на листе.
- **Исправление:**
  1. **Обнулить padding на сторонах портов:** `pad_value=["15mm", "15mm", "0mm", "0mm", "15mm", "0mm"]` — плоскость порта совпадает с границей Region.
  2. **Сдвинуть PEC-стенки внутрь Region** (иначе окажутся снаружи объёма):
     ```python
     if direction > 0:
         wall_y_origin = y0 - 2.0 * t_cu_mm - 0.1   # внутрь (в -Y)
     else:
         wall_y_origin = y0 + 0.1                    # внутрь (в +Y)
     ```
  3. Координаты листа и `integration_line` оставить одинаковыми (Python-числа).
- **Влияние:** порты создаются без ошибок; PEC-рамки внутри Region выполняют роль задней стенки.
- **Урок:**
  1. **`Wave Port` в HFSS должен лежать на внешней границе** модели (Region / AirBox / PML). Порт «внутри» объёма невозможен.
  2. **При использовании Open Region padding на сторонах портов должен быть 0.**
  3. **PEC-стенки для портов** — располагать **внутрь** Region (на `+0.1 мм` от порта вглубь).
  4. **Симптом `Both endpoints` имеет два разных источника:** (а) рассогласование координат листа и `integration_line` (DL-47), (б) порт не на границе Region (DL-51).

## Раздел D. API, парсинг, HFSS-операции

### DL-03 — DL-05. Переименования в PyAEDT 1.8.0
- `Hfss(projectname=...)` → `Hfss(project=...)`
- `new_desktop_session=True` → `new_desktop=True`
- `create_box(position=..., dimensions=...)` → `create_box(origin=..., sizes=...)`
- **Урок:** сверять сигнатуры при переходе на новые версии.

### DL-06 — DL-08. Чтение переменных
- `GetVariableValue` возвращает строку с единицами, не раскрывает выражения. `hfss[name]` возвращает `str`.
- **Исправление:** `hfss.get_evaluated_value(name)` (число в СИ) × 1000 → мм.
- **Урок:** для вычисленных значений — только `get_evaluated_value`.

### DL-09. `modeler.intersect` модифицирует первый объект in-place
- `intersect([obj1, obj2])` модифицирует `obj1`, удаляет `obj2`.
- **Урок:** логические операции — in-place.

### DL-10, DL-15, DL-20. Ограничения HFSS-выражений
- Нельзя использовать Python-имена (`W_mm`) (DL-10).
- Нельзя использовать унарный `+` в начале выражения (DL-15).
- Сложные `sqrt`/`pi` цепочки не парсятся (DL-20).
- **Урок:** сложные формулы считать в Python, передавать готовые числа. Простые зависимости — через HFSS-выражения без унарного `+`.

### DL-11, DL-14. `integration_line` — только числа
- Передача строк приводит к ошибке длины. Числа относительны порта и движутся за ним.
- **Урок:** `integration_line` — только числа (float); пересборка портов не требуется.

### DL-12. Порядок операций: порты → setup → sweep
- Interpolating sweep требует наличия хотя бы одного порта.

### DL-21. `subtract` с `keep_originals=False` удаляет tool-объекты
- При множественном вычитании — сохранять оригиналы (`keep_originals=True`) до последнего вызова.

### DL-22. Python-переменная в HFSS-выражении `AirBox`
- Переменные Python должны быть объявлены в HFSS (`hfss["L_coax"] = ...`).

### DL-23. `unite` удаляет исходные объекты
- После `unite([A, B, C])` существует только `A`.

### DL-25. `'r_outer' is not a defined variable` при создании стенки разъема
- Радиусы коаксиала должны быть объявлены в HFSS (`hfss["r_outer"] = ...`).
- **Урок:** любые параметры в строках HFSS-выражений должны быть переменными дизайна HFSS.

### DL-35. `'conn_ins_depth' / 'conn_hole_x' is not a defined variable` в HFSS-выражениях
- **Симптом:** `[error] 'conn_ins_depth' is not a defined variable name in this context`.
- **Первопричина:** При построении выражений для пазов и площадок использовались Python-переменные, не объявленные как HFSS-переменные.
- **Исправление:** Все параметры разъема добавлены в дерево переменных HFSS.
- **Урок:** Любая переменная в `origin` / `sizes` должна быть либо числом, либо объявленной HFSS-переменной.

### DL-38. `NameError: L_thru_val` при переходе на Python-предвычисления
- **Симптом:** `NameError: name 'L_thru_val' is not defined`.
- **Первопричина:** При массовом переносе вычислений в Python (для устранения DL-39) ассистент переименовал локальные переменные, но забыл, что функция `draw_coax_and_port` ожидает именно `L_thru_val`.
- **Исправление:** Явно добавлено `L_thru_val = L_thru_mm` в блок предвычислений.
- **Урок:** при рефакторинге проверить все точки вызова функций, использующих эти переменные.

### DL-39. `Parasolid Error: body lying outside size box` из-за строковых координат
- **Симптом:** серия ошибок `[error] Parasolid Error: The transformation would result in body lying outside the size box`.
- **Первопричина:** HFSS-парсер не справлялся с цепочкой вложенных выражений, содержащих `mm`-суффиксы в комбинации с арифметикой. В результате координата Z получала `NaN` или огромное значение.
- **Исправление:** Все сложные формулы предвычислены в Python и переданы в HFSS как готовые числа.
- **Урок:** при использовании `create_cylinder`, `create_circle`, `create_box` в циклах с переменными — передавать числовые значения.

### DL-48. `Invalid solution type` — ложная ошибка после провала `is_microstrip` (try/except fallback)
- **Когда:** v3.4.0, fallback-вызов `wave_port` без `is_microstrip=True`.
- **Симптом:**
  ```
  [warn] is_microstrip failed: Failed to create boundary Wave Port P_THRU_1, using explicit integration_line
  [error] Invalid solution type. on wave_port
  ```
  Хотя `solution_type="DrivenModal"` задан в `Hfss(...)`.
- **Первопричина:** В PyAEDT 1.8.0 после **неудачной** попытки `wave_port(is_microstrip=True)` дизайн остаётся в некорректном состоянии. Повторный `wave_port` падает с **обманчивой** ошибкой `Invalid solution type`.
- **Исправление (v3.4.1):** Убрать `is_microstrip=True` и `try/except fallback` полностью. Один чистый вызов `wave_port`.
- **Урок:** В PyAEDT 1.8.0 **не** использовать `try/except` вокруг `wave_port`.

### DL-49. `is_microstrip=True` не работает в PyAEDT 1.8.0 при объединённой земле
- **Когда:** v3.4.0, `wave_port(..., is_microstrip=True, reference="GND_BOT")`.
- **Симптом:** `Failed to create boundary Wave Port P_THRU_1`.
- **Первопричина:** В модели `GND_BOT` объединён в один объект с `GND_LINE`, `GND_OPEN`, `GND_RES`, `GND_Bridge_*`. PyAEDT при `is_microstrip=True` ищет **плоскость земли** под портом, но находит объединённый объект сложной формы.
- **Исправление (v3.4.1):** Отказаться от `is_microstrip=True`. Использовать явную `integration_line`.
- **Урок:** `is_microstrip=True` в PyAEDT 1.8.0 работает только для простой геометрии.

### DL-52. `Object3d` has no attribute `face_centers`, `Modeler3D` — `get_face_ids` (PyAEDT 1.8.0)
- **Когда:** v3.5.2, попытка найти грань через `obj.faces` / `obj.face_centers` или `hfss.modeler.get_face_ids` / `get_face_center`.
- **Симптом:**
  ```
  [warn] obj.faces/.face_centers failed: 'Object3d' object has no attribute 'face_centers'
  [warn] modeler.get_face_ids failed: 'Modeler3D' object has no attribute 'get_face_ids'
  ```
- **Первопричина:** В PyAEDT 1.8.0 методы `face_centers` и `get_face_ids` отсутствуют. Есть только `oeditor.GetFaceIDs` / `GetFaceCenter` (низкоуровневый API).
- **Исправление (v3.5.3):** Использовать `hfss.modeler.oeditor.GetFaceIDs(obj_name)` → список face ID (строки); `hfss.modeler.oeditor.GetFaceCenter(fid)` → центр грани.
- **Урок:** В PyAEDT 1.8.0 для работы с гранями — только `oeditor.*`. Публичные `modeler.get_face_ids` / `face_centers` появились позже.

### DL-53. `a geometry selection is required for assignment` — `wave_port(assignment=face_id)`
- **Когда:** v3.5.4, `hfss.wave_port(assignment=face_id, ...)` где `face_id = "771"` (строка face ID).
- **Симптом:**
  ```
  [error] port 'p_thru_1': a geometry selection is required for assignment.
  props = {'Objects': ['771'], ...}
  ```
- **Первопричина:** `hfss.wave_port()` в PyAEDT 1.8.0 кладёт `assignment` в `props['Objects']`. Для face ID это неверно: HFSS ожидает `Objects:=[]` и `Faces:=[771]`. PyAEDT 1.8.0 не поддерживает назначение порта на грань через `wave_port()`.
- **Исправление (v3.5.5):** Использовать низкоуровневый `hfss.oboundary.AssignWavePort(props)`, где `props` содержит `Objects:=[], Faces:=[771], NAME:P_xxx`. Fallback — `hfss.modeler.oeditor.AssignWavePort(props)`.
- **Урок:** В PyAEDT 1.8.0 `wave_port()` предназначен только для листов (`Objects`). Для граней — только `AssignWavePort(props)` с массивом `Faces`. Формат `props` — список `["NAME:xxx", "Objects:=", [], "Faces:=", [771], "NumModes:=", 1, ...]`.

### DL-54. `GetFaceIDs` / `GetFaceCenter` — парсинг форматов в AEDT 2025.1
- **Когда:** v3.5.3, первая попытка использовать `GetFaceCenter`.
- **Симптом:** тихое падение — функция возвращала `None` на всех гранях, `RuntimeError: Не найдена грань`.
- **Первопричина:** `GetFaceCenter` может возвращать координаты в разных форматах: `str` (`"(-25.0, -5.0, 0.93)mm"`), `list[float]`, `tuple[float]`. Единицы — СИ (м) или `model_units` (мм). Без парсинга и авто-конверсии `if abs(y) < 1.0: y *= 1000` — поиск не работает.
- **Исправление (v3.5.4):** Функция `_parse_coord(v)` — универсальный парсер (str/list/tuple/float). Функция `_get_face_y(obj, fid)` — пробует `GetFaceCenter`, затем `GetFaceVertexPositions` (среднее Y по вершинам). Авто-конверсия единиц. Диагностический `print` для каждой грани.
- **Урок:** `oeditor.GetFaceCenter` в AEDT 2025.1 — возвращает координаты в формате, зависящем от версии и `model_units`. Всегда парсить и проверять единицы (СИ vs `model_units`). Для надёжности — fallback через `GetFaceVertexPositions` и среднее по вершинам.

- **Урок:** Правила §2.6 (краткость) и §5.1 (минимальный дифф) — обязательны.
