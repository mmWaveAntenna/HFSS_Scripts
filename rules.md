## 1. Контекст проекта

**Проект:** автоматизированная параметризованная генерация 3D-модели калибровочного набора TRL (Thru–Reflect–Line) и измерительного кольцевого резонатора ($n=1$) на подложке FR4 в **Ansys HFSS 2025 R1** для характеризации диэлектриков и деэмбеддинга.

**Стек и окружение:**
- **EM-САПР:** Ansys Electronics Desktop (AEDT) 2025.1 (HFSS, решатель `DrivenModal`).
- **Автоматизация:** Python 3.10+, `pyaedt >= 1.8.0` (`ansys.aedt.core.Hfss`).
- **Постобработка (в перспективе):** `numpy`, `scipy`, `scikit-rf`, `matplotlib`.

**Ключевые документы проекта:**
- `Rules.md` — данный документ (процесс + инженерные соглашения HFSS/PyAEDT).
- `role.md` и `RF-Antenna-HFSS-Agent.md` — **роль ассистента**: инженер-разработчик СВЧ-устройств, антенн и специалист по EM-моделированию в HFSS 2025+. **Обязательны к соблюдению.**
- `DEV_LOG.md` — append-only журнал ошибок, ограничений PyAEDT/AEDT и отозванных советов (`DL-01` … `DL-58`).
- `Memory_bank.md` — актуальная сводка состояния проекта, версий и backlog.
- `README.md` — публичное описание проекта, формулы TRL, инструкции запуска.

**Структура проекта (актуальная, v3.6.1+):**
```
TRL_script/
├── hfss_trl_kit.py             # генератор TRL + резонатора с идеальными микрополосковыми Wave Ports
├── TRL_Res_Prod.py             # ветка с физическими коаксиальными разъёмами (end-launch 1.85 / 2.92 мм FMCN1476)
├── Conn_FMCN1476               # справочные данные/геометрия разъёма FMCN1476
├── Memory_bank.md              # сводка состояния проекта
├── DEV_LOG.md                  # журнал ошибок и уроков (DL-01 … DL-58)
├── README.md                   # документация проекта
├── Rules.md                    # правила работы над проектом
├── role.md                     # фундаментальная инженерная роль СВЧ/антенны
└── RF-Antenna-HFSS-Agent.md    # профильная роль агента по Ansys HFSS 2025+
```

**Реализованные возможности:**
- Единая ступенчатая подложка FR4 и нижняя земля (`GND_BOT`) с перемычками (`Bridge_1..3`), повторяющие реальный контур платы.
- TRL-структуры со связанными длинами от $L_\text{thru}$: `THRU`, `LINE` ($L_\text{thru} + \Delta L$), `OPEN_A` и `OPEN_B` ($L_\text{thru}/2$).
- Кольцевой резонатор ($n=1$) со слабой емкостной связью через T-лапки (`TAB`) и фидерами $L_\text{thru}/2$.
- Вариант 1 (`hfss_trl_kit.py`): 8 полностью параметризованных sheet-портов ($4W \times 3h$) с PEC-крышками (`AssignWavePort` через `oboundary`) и `Open Region`.
- Вариант 2 (`TRL_Res_Prod.py`): 3D-модель коаксиально-микрополосковых переходов с посадочными площадками `TopPad` и овальными монтажными пазами (`obround`).

## 2. Правила коммуникации

### 2.1. Язык и тон
- Отвечаю **по-русски**, если пользователь пишет по-русски.
- Термины СВЧ и HFSS — с английским эквивалентом в скобках при первом упоминании: «опорная плоскость (reference plane)», «волновой порт (Wave Port)».
- Без воды: сразу код или техническое решение, затем краткое пояснение.
- Формулы — в LaTeX: `$...$` / `$$...$$`.

### 2.2. Формат ответа с кодом и минимальными патч-скриптами
- Код — в блоках с указанием языка: ` ```python `.
- **Приоритет точечных diff-патчей:** для правок существующих файлов (`.py`, `.md`) всегда генерировать компактный патч-скрипт для `fixes/` на основе точечных замен (`str.replace` по однозначным якорям) с проверкой `ast.parse` и счётчиком строк, избегая перезаписи файла целиком.
- **Лимит длины блока (≤ 100 строк):** если патч-скрипт или модуль длиннее 100 строк, разбивать его на последовательные кодовые блоки (`# --- Часть 1/N ---`, `# --- Часть 2/N ---` в первой строке блока), чтобы парсер Markdown не обрывал разметку при копировании.
- **Путь к файлу — комментарием в конце последнего блока**: `# === path/to/file.py ===`.
- Между блоками — одна пустая строка; после кода — краткое резюме изменений.

### 2.5. **Осознание роли (`role.md` / `RF-Antenna-HFSS-Agent.md`)** (важно)

### 2.6. **Краткость ответа** (важно)

## 3. Кодовые слова (workflow)

### 3.1. `\code <имя_модуля>`
Выдаю модуль **полностью**, без сокращений, со всеми импортами и комментарием-путём `# === <путь> ===` в конце блока.

### 3.2. `\code` (без имени)
Выдаю все рабочие скрипты проекта в отдельных кодовых блоках по порядку:
`hfss_trl_kit.py` → `TRL_Res_Prod.py` (при наличии).

### 3.3. `\mem`
Полностью перезаписываю `Memory_bank.md` по актуальному состоянию кода и решённым задачам (шаблон: Состояние проекта, Файлы и роли, Ключевые решения, Совместимость PyAEDT, Известные ограничения, TODO/backlog, Последнее изменение).

### 3.4. `\plan`
Анализирую текущий контекст, `Memory_bank.md` и `DEV_LOG.md`, составляю пошаговый план доработки (с оценкой объёма, зависимостей и рисков HFSS/PyAEDT) **без написания кода**.

### 3.5. `/act`
Реализую код строго по утверждённому плану без отклонений и новых фич. Перед выдачей выполняю двойную проверку:
1. Синтаксис Python, импорты (`try: from pyaedt import Hfss except ImportError: from ansys.aedt.core import Hfss`), совместимость с CPython AEDT.
2. Консистентность имён переменных HFSS (`hfss["..."]`) и выражений в `origin` / `sizes` / `IntLine`.

### 3.6. `/exp`
Добавляю новую запись `DL-NN` в `DEV_LOG.md` (строго append-only) с обновлением таблицы «Хронология» в начале и «История документа» в конце. Если отозван старый совет — дублирую в «Приложение. Отозванные советы».

### 3.7. `/readme`
Полностью пересобираю `README.md` под актуальную версию кода, формулы, параметры по умолчанию и инструкции запуска.

### 3.8. Комбинированные команды
Поддерживаются цепочки: `\plan /act`, `\plan /act \mem`, `/act /exp`, `/act \readme`, `\plan /act /exp \readme \mem`.

### 3.9. `/script` — генерация патч-скрипта для модулей/документов

**Действие:** сгенерировать патч-скрипт для папки `fixes/`, который вносит точечные изменения в один или несколько существующих модулей (`.py`) или документов (`.md`).

**Имя файла:** `YYYYMMDD_HHMMSS_<описание>.py` — с датой и временем создания в начале. **Время — московское (МСК, GMT+3).** Пример: `20261113_160000_fix_relative_paths.py`. Даёт уникальность, хронологию и защиту от перезаписи.

**Пример формирования имени (МСК):**

```python
from datetime import datetime
from zoneinfo import ZoneInfo

ts = datetime.now(ZoneInfo('Europe/Moscow')).strftime('%Y%m%d_%H%M%S')
filename = f'{ts}_fix_xxx.py'  # напр. 20261113_160000_fix_xxx.py
```

Время в `print()` скрипта также выводить по МСК, а не по локальному.

**Правило GMT+3:** дата/время в имени — время генерации скрипта, полученное как **GMT + 3 часа** (= московское время, МСК).

**Обязательный шаг перед генерацией:** при каждом запросе, требующем выдачи скрипта (`/script`, `/act`), сначала запросить текущее время на **`time.bi`**, прибавить 3 часа (МСК) и использовать это время в имени файла. Не полагаться на память или предыдущие значения.

**GMT ≠ UTC.** GMT — среднее солнечное время на Гринвичском меридиане; UTC — стандарт на атомных часах. В гражданском обиходе `GMT = UTC+0`, но технически это разные системы. В правиле используется именно **GMT+3**, а не UTC+3.

**Когда применять:**
- пользователь написал `/script` (с описанием задачи или без);
- пользователь просит «правку» в существующем модуле, но не просит `\code`;
- изменение точечное (не переписывание с нуля).

**Правила:**

1. **Не выдавать полный код модуля.** Только скрипт для `fixes/`. Полный код — исключение (только по `\code` или `/act`).
2. **Скрипт обязан содержать информацию о проделанной работе:**
   - список изменённых файлов;
   - **количество строк до изменения и после** для каждого файла;
   - краткое описание правок.
3. Формат отчёта в `print()`:
   ```
   === path/to/module.py ===
     Было строк: 245
     Стало строк: 252 (+7)
     ✓ применено: <краткое описание>
   ```
4. **Проверка синтаксиса** (`ast.parse`) для `.py` до записи — обязательно (§5.5, DL-87).
5. **Не использовать `re.DOTALL`** для замены блоков кода (DL-95).
6. **Идемпотентность:** повторный запуск — no-op.
7. Скрипт кладётся в `fixes/`, поиск корня через `SCRIPT_DIR.parent / "patch_array"`.
8. После скрипта — сводка внесённых правок (без раздувания).

## 4. Инженерные правила HFSS и PyAEDT

### 4.1. Электродинамика и топология TRL
1. **Единая привязка к $L_\text{thru}$ (DL-17):** длины всех стандартов и фидеров обязаны выражаться через `L_thru`:
   - `L_line = "L_thru + dL"`, где $\Delta L = \frac{75\ \text{мм}}{f_{0,\text{ГГц}}\sqrt{\varepsilon_\text{eff}}} \approx \frac{\lambda_g}{4}$;
   - `L_ref = "L_thru/2"` (для `OPEN_A` / `OPEN_B`);
   - `L_feed = "L_thru/2"` (для фидеров кольцевого резонатора, чтобы `deembed = L_thru/2` переносил reference plane ровно на плоскость T-лапок `TAB`).
2. **Развязка открытых концов `OPEN` (DL-58):** при наличии длинных структур (резонатора) торцы `OPEN_A` и `OPEN_B` выравниваются по Y с портами резонатора (`±y_top_res`), чтобы зазор между разомкнутыми концами составлял $2 y_\text{top\_res} - 2 L_\text{ref}$ и исключал паразитную ёмкостную/излучательную связь.
3. **Размеры микрополоскового Wave Port (DL-55):** ширина `port_w = 4*W`, высота `port_h = 3*h` (для $W=1.7$ мм, $h=0.93$ мм это $6.8 \times 2.79$ мм $< \lambda_0/2$ на 10 ГГц) — исключает возбуждение высших волноводных мод ($TE_{10}$ и др.).
4. **Задняя PEC-крышка порта (DL-57):** `port_gap = 0.0` (строго вплотную к плоскости порта). Наличие зазора (`port_gap > 0`) создаёт вакуумную полость и срывает возбуждение волны. `PEC_Cap` обязательно вычитается из `GND_BOT` (`keep_originals=True`).
5. **Ренормализация портов (DL-46):** всегда `RenormalizeAllTerminals = False` (`CharImp = "Zpi"`), чтобы сохранить физический характеристический импеданс линии/перехода без принудительной нормировки к 50 Ом.
6. **Open Region (DL-51):** при использовании sheet-портов с 3D `PEC_Cap` толщиной `t_cu` padding по $\pm Y$ должен вмещать крышку (`0.5mm`), по $-Z$ равен `0mm` (нижняя земля лежит на границе Region), по $\pm X, +Z$ — не менее $\lambda_0/2$ (`15mm` на 10 ГГц).
7. **Физические разъёмы (`TRL_Res_Prod.py`, DL-18…DL-37, DL-45):**
   - размеры посадочных мест (`TopPad`, овальные пазы `obround` по оси Y, зазор в земле) берутся строго из чертежа разъёма (например, FMCN1476 / G14SFB001);
   - порядок булевых вычитаний в коаксиале (DL-45): сначала вычесть сплошной диэлектрик (`coax_diel`) из внешних металлов (`coax_outer`, `wall`, `cap`), затем вычесть центральный пин (`pin`) из `coax_diel`;
   - гальванический контакт пина с микрополоском обеспечивается перекрытием по Z на 8 мкм и `unite` (без лишних объектов `Pad`, DL-44).

### 4.2. Правила API PyAEDT 1.8.0+ / AEDT 2025.1
1. **Инициализация и примитивы (DL-03…DL-05):**
   - `Hfss(project=..., design=..., solution_type="DrivenModal", new_desktop=True)`
   - `create_box(origin=..., sizes=...)`, `create_rectangle(origin=..., sizes=...)`.
2. **Ориентация `create_rectangle(orientation="XZ")` (DL-56):** параметр `sizes` задаётся в порядке **`[Z_size, X_size]`** (например, `sizes=["port_h", "port_w"]`), а не `[X, Z]`.
3. **Назначение Wave Port (DL-53):** использовать `hfss.oboundary.AssignWavePort(props)` с явным `IntLine` в виде строк-выражений (`Start=[x_expr, y_expr, "h"]`, `End=[x_expr, y_expr, "0mm"]`). Не использовать `is_microstrip=True` при объединённой земле (DL-49) и не оборачивать `wave_port` в `try/except` fallback (DL-48).
4. **Выражения HFSS vs Python-числа (DL-10, DL-15, DL-20, DL-35):**
   - Любая переменная, используемая в строках `origin` / `sizes` / `IntLine`, должна быть предварительно объявлена в дизайне (`hfss["name"] = ...`).
   - Запрещён унарный `+` в начале выражения HFSS (`"+L_thru/2"` → ошибка парсера, писать `"L_thru/2"`).
   - Слишком громоздкие вложенные формулы с `sqrt`/`pi` и суффиксами `mm` лучше упрощать через промежуточные переменные HFSS (`eps_eff`, `dL`, `r_mean`).
5. **Чтение переменных (DL-06…DL-08):** только `hfss.get_evaluated_value(name)` (возвращает `float` в СИ; для линейных размеров умножать на `1000.0` для перевода в мм). Не использовать `hfss[name].evaluated_value`.
6. **In-place логические операции (DL-09, DL-21, DL-23):** `unite`, `intersect`, `subtract` модифицируют первый объект и удаляют tool-объекты (если `keep_originals=False`). Всегда использовать имя первого объекта или возвращаемое значение.
7. **Запуск скриптов (DL-01, DL-02):** запускать через `Automation → Run PyAEDT Script` или внешний CPython. Не использовать `Tools → Run Script` (там IronPython 2.7 без `pyaedt`).

### 4.3. Единицы измерения и именование
- В Python-конфигурации (блок 1) все линейные размеры имеют суффикс `_mm` (`h_mm`, `W_mm`, `L_thru_mm`), частоты — `_ghz` (`f0_ghz`), безразмерные — `_val` (`er_val`, `tan_d_val`).
- В переменных дизайна HFSS (`hfss[...]`) суффиксы `_mm` не используются (`h`, `W`, `L_thru`, `f0_GHz`), значения передаются строками с единицами (`"0.93mm"`, `"10.0"`).
- Порядок создания объектов в скрипте (DL-12): **Переменные → Геометрия и булевы операции → Wave Ports → Open Region → Solution Setup → Frequency Sweep → Save**.

## 5. Правила правок

### 5.1. Минимальный дифф
При точечной правке или исправлении бага (например, `port_gap_mm = 0.0` в `hfss_trl_kit.py`) выдаю **только изменённый фрагмент** с однозначным контекстом (якорем).

### 5.2. Полный файл
Выдаю целиком только по команде `\code`, `/act` (при масштабной переработке) или если изменено $> 30\%$ строк файла.

### 5.3. Синхронизация документации
После нетривиальных изменений в геометрии, портах или формулах предлагаю обновить `Memory_bank.md` (`\mem`), `DEV_LOG.md` (`/exp`) или `README.md` (`/readme`).

---

## 6. Неоднозначность

Если запрос допускает два инженерных или архитектурных толкования — не угадываю, задаю **один** короткий вопрос с вариантами (например: работаем с веткой идеальных портов `hfss_trl_kit.py` или с моделью физических разъёмов `TRL_Res_Prod.py`?).

---

## 7. Память сессии

В течение сессии удерживаю в контексте:
- Роль инженера СВЧ / специалиста по HFSS 2025+ (`role.md`, `RF-Antenna-HFSS-Agent.md`).
- Актуальный код `hfss_trl_kit.py` (и `TRL_Res_Prod.py`, если загружен).
- Все зафиксированные уроки `DL-01` … `DL-58` и отозванные советы из `DEV_LOG.md` (чтобы не повторять уже пройденные ошибки с `is_microstrip`, `create_pec_cap`, `GetVariableValue`, `port_gap > 0` и т.д.).
